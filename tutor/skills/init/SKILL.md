# Tutor Init

Set up tutorial writing configuration for this project.

## Step 1: Gather project context

Read the project's README.md, CLAUDE.md, package.json, pyproject.toml, Cargo.toml, or other package metadata to infer:
- Project name and one-line summary
- Primary language and frameworks
- Key domain concepts

Present the inferred summary to the user for confirmation. If no metadata is found, ask the user to describe the project.

## Step 2: Ask preferences

Use AskUserQuestion for each of these (batch into as few calls as possible):

**Audience** — Who reads these tutorials?
- Developers on my team
- OSS contributors
- Non-technical stakeholders
- (Other — free text)

**Technical level** (if technical audience):
- Beginner
- Intermediate
- Expert

**Baseline knowledge** — Multi-select from project-relevant topics inferred from the codebase (e.g., "Python", "React", "Docker", "SQL"). These are things you will NOT explain in tutorials.

**Focus areas** — Multi-select, then ask weight (light/normal/heavy) for each selected:
- Why decisions were made (design_choices)
- How the code works (implementation)
- How to use it (examples)
- How it fits together (connections)
- Core concepts (conceptual)

**Style** — Pick one:
- Narrative walkthrough ("First we... then we... because...")
- Reference docs (structured sections, lookup-friendly)
- FAQ format (question-answer pairs)

**Trigger mode** — When should tutorials be written?
- Manual only (call /tutor:write yourself)
- Before implementation (write tutorial first, then code)
- After implementation (write tutorial after code is done)
- Both (before and after — plan then update)

## Step 3: Write config

Write `.tutor/config.yaml` with the gathered preferences. Follow this schema:

```yaml
# Generated by /tutor:init — edit freely
project:
  summary: "<one-line project description>"

audience:
  profile: "<free text audience description>"
  technical_level: intermediate  # beginner | intermediate | expert
  assumed_knowledge:
    - <list of things NOT to explain>

focus:
  conceptual: normal        # skip | light | normal | heavy
  design_choices: heavy
  implementation: heavy
  connections: normal
  examples: heavy

triggers:
  mode: manual              # manual | pre | post | both

output:
  directory: tutorials/
  style: narrative          # narrative | reference | faq
  naming: "{nn}-{slug}.md"
  frontmatter: true
  frontmatter_fields:
    - date
    - summary
    - audience

presets:
  quick:
    focus_override:
      conceptual: light
      implementation: skip
    length: brief
  deep-dive:
    focus_override:
      conceptual: heavy
      design_choices: heavy
      implementation: heavy
      connections: heavy
      examples: heavy
    length: comprehensive
```

Populate all values based on the user's answers. Do NOT leave placeholders.

## Step 4: Generate GUIDE.md

Write `.tutor/GUIDE.md` — a writing guide tailored specifically to THIS project's audience and focus settings. This is NOT a generic template. Generate it fresh based on the config.

The guide MUST include:

### Audience section
Based on technical_level, write specific adaptation rules:
- **Beginner**: Define every term on first use, use analogies, no unexplained jargon, show complete runnable examples, explain what output means
- **Intermediate**: Assume language fluency, introduce project-specific libraries on first use (one sentence), focus on project-specific decisions, code fragments OK if context is clear
- **Expert**: Skip fundamentals, focus on non-obvious tradeoffs and edge cases, discuss architectural reasoning in depth, code examples focus on subtle behavior

### Section weights table
Map each focus area to its weight and describe what to write at that weight:
- **skip**: Omit entirely
- **light**: 1-2 sentences, no dedicated section
- **normal**: Standard paragraph-level coverage
- **heavy**: Dedicated section, go deep, this is a primary draw

### Style rules
Write specific rules for the chosen style (narrative / reference / faq).

### Frontmatter requirements
Specify the exact YAML frontmatter format every tutorial must start with.

### Naming convention
Show the naming pattern with examples using actual project topics.

### Quality bar
Define what the target reader should be able to do after reading a tutorial.

## Step 5: Generate CLAUDE.md snippet (if not manual mode)

If trigger mode is NOT "manual", append a clearly-marked section to the project's CLAUDE.md (create the file if it doesn't exist). The snippet should be wrapped in HTML comments for easy identification:

**For "pre" mode:**
```
<!-- tutor:triggers — auto-generated by /tutor:init, edit freely -->
## Tutorial-First Development
Before implementing any new feature, phase, or significant code change,
run `/tutor:write` to create a tutorial covering the planned work.
The tutorial should explain the design, approach, and reasoning BEFORE
code is written. This ensures clarity of thought and creates documentation
as a side effect of planning.
<!-- /tutor:triggers -->
```

**For "post" mode:**
```
<!-- tutor:triggers — auto-generated by /tutor:init, edit freely -->
## Post-Implementation Tutorials
After completing a new feature, phase, or significant code change,
run `/tutor:write` to create or update a tutorial covering what was
built. The tutorial should explain the final design, key decisions
made during implementation, and how the code works.
<!-- /tutor:triggers -->
```

**For "both" mode:**
```
<!-- tutor:triggers — auto-generated by /tutor:init, edit freely -->
## Tutorial-Driven Development
Before implementing any new feature or significant change, run
`/tutor:write` to draft a tutorial covering the planned approach.
After implementation is complete, run `/tutor:write --update` to
revise the tutorial to reflect what was actually built.
<!-- /tutor:triggers -->
```

If reconfiguring (CLAUDE.md already has a `<!-- tutor:triggers -->` block), find and replace the existing block. If switching to "manual", remove the block entirely.

## Step 6: Create tutorials directory

Create the `tutorials/` directory if it doesn't exist.

Confirm setup is complete and summarize:
- Config written to `.tutor/config.yaml`
- Writing guide generated at `.tutor/GUIDE.md`
- Trigger mode and any CLAUDE.md changes
- Ready to use `/tutor:write` and `/tutor:ask`
